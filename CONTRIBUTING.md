# Contributing

Правила работы с репозиторием для всех участников.

## Быстрый старт

```bash
docker compose up -d          # Postgres, MinIO, Grafana (dev), Api, Worker
dotnet build
dotnet test
```

Перед пушем: `dotnet format` — CI проверяет форматирование и падает при расхождениях.

## Задачи

- Работа ведётся только по issue из backlog. Нет issue — сначала заведите его.
- Берёте задачу — назначьте себя исполнителем и переведите в «In progress».
- Задача с оценкой L при взятии дробится на подзадачи, каждая — отдельный pull request.

## Ветки

- `main` — защищённая ветка, всегда собирается и проходит тесты. Прямые пуши запрещены.
- Рабочая ветка создаётся от `main` и называется так:

```
<тип>/<номер-issue>-<краткое-описание>
```

| Тип        | Когда                                   |
|------------|-----------------------------------------|
| `feature`  | новая функциональность                  |
| `fix`      | исправление ошибки                      |
| `refactor` | изменение кода без изменения поведения  |
| `test`     | только тесты                            |
| `docs`     | только документация                     |
| `chore`    | сборка, CI, зависимости, инфраструктура |

Примеры: `feature/5-report-settings`, `fix/9-retry-backoff`, `chore/1-docker-compose`.

- Описание — латиницей, в нижнем регистре, слова через дефис, 2–4 слова.
- Ветка живёт недолго: цель — влить её за 1–3 дня. Перед review обновите ветку от `main` через `git rebase main`.

## Коммиты

Используем [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <что сделано>

<необязательное тело: зачем и что важно знать>

Refs #<номер-issue>
```

**Типы:** `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `perf`.

**Области:** `api`, `engine`, `steps`, `grafana`, `worker`, `infra`, `client`, `delivery`.

Правила:

- Заголовок — на английском, в повелительном наклонении, со строчной буквы, без точки, до 72 символов: `feat(engine): add optimistic concurrency to job transitions`.
- В теле объясняйте *почему*, а не *что* — что видно из диффа.
- Один коммит — одно логическое изменение. Не смешивайте рефакторинг и новую функциональность.
- Ломающее изменение API или схемы БД помечается `!` после области и строкой `BREAKING CHANGE:` в теле.
- В последней строке — ссылка на issue: `Refs #5`. В pull request используйте `Closes #5`, чтобы issue закрылось при слиянии.

## Pull request

- Один pull request — одно issue (или одна подзадача L-issue).
- Заголовок PR — в формате Conventional Commits: при squash-слиянии он станет коммитом в `main`.
- В описании: что сделано, как проверить, ссылка `Closes #N`, скриншот или пример ответа API, если менялось поведение.
- Размер — до ~400 строк изменений без учёта сгенерированного кода и миграций. Больше — делите.
- Черновик открывайте как Draft, чтобы получить ранний отзыв.
- Слияние — только **Squash and merge**, после слияния ветка удаляется.

## Review

**Кто:**

- Каждый PR одобряет минимум **один** участник, кроме автора.
- Ревьюера назначает автор PR.

**Как:**

- Ревьюер отвечает в течение **одного рабочего дня**. Не успеваете — напишите автору и передайте review другому.
- Проверяйте по порядку: соответствие критериям приёмки issue → корректность переходов Job и обработку ошибок → тесты → читаемость.
- Комментарии помечайте префиксом:
    - `blocker:` — без исправления нельзя сливать;
    - `question:` — нужно пояснение;
    - `nit:` — мелочь, на усмотрение автора.
- Автор отвечает на каждый комментарий: исправлением или пояснением. Разрешает обсуждение тот, кто его открыл.
- Сливает PR автор после одобрения и зелёного CI. Сливать свой PR без одобрения нельзя.

## Definition of Done

Задача считается сделанной, когда выполнено **всё** из списка:

1. **Критерии приёмки** из issue и связанного сценария (SC) в документе требований выполнены, по каждому есть автотест.
2. **Тесты:** юнит-тесты на логику; интеграционные — с Testcontainers (Postgres, MinIO) и WireMock.Net (Grafana) для всего, что ходит во внешние системы. Ошибочные пути покрыты так же, как успешные.
3. **CI зелёный:** сборка, `dotnet format`, все тесты, проверка OpenAPI-диффа.
4. **API:** при изменении контракта OpenAPI-документ и клиент пересобраны, ломающие изменения согласованы и помечены.
5. **База данных:** миграция EF добавлена, применяется на чистой БД и поверх предыдущей версии.
6. **Жизненный цикл Job:** новые состояния и переходы добавлены в таблицу переходов и в документ требований; каждый переход пишется в `job_events`.
7. **Наблюдаемость:** ошибки и переходы логируются со `jobId` и `reportId`, секреты и токены в логи не попадают.
8. **Документация:** README и этот файл обновлены, если изменился способ запуска, конфигурация или процесс.
9. **Review:** PR одобрен по правилам выше, все `blocker:` закрыты.
10. **Проверено вживую:** сценарий воспроизводится в `docker compose` — автор приложил в PR шаги проверки.
11. **Слито в `main`**, issue закрыто, ветка удалена.

Не выполнен хотя бы один пункт — задача остаётся «In review» или «In progress», а не «Done».
