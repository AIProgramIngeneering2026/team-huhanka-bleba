# Проверка контракта колодой

Проходим по контракту картами контрактного покера К1–К10
([колода](https://github.com/AIProgramIngeneering2026/Zadania/blob/main/tasks/p2_poker/README.md#колода)).
Контракт — это [openapi.yaml](api/openapi.yaml), [tool-contract.md](tool-contract.md),
[диаграмма состояний Job](architecture.md#диаграмма-состояний-job) и ADR в [adr/](adr/).

| Карта                              | Ответ контракта                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
|------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **К1 Двойной клик**                | Два `POST /reports/{reportId}/jobs` с одним `Idempotency-Key` → первый `202`, второй `200` с тем же Job и `Idempotent-Replayed: true`; Job один. Без ключа второй запрос получает `409 job_already_active` с `details.jobId` — один незавершённый Job на «отчёт + период». [openapi.yaml](api/openapi.yaml): `runReport`, параметр `IdempotencyKey`, ответ `JobConflict`; [ADR-0002](adr/0002-duplicate-request-protection.md). Двойная отмена — `200` с тем же Job: `cancelJob`                                                                                                                                                                                                                                                |
| **К2 Ответ потерялся**             | Клиент повторяет запрос с тем же `Idempotency-Key` и получает исходный Job (`200`), новый не создаётся. Без ключа — `409 job_already_active` со ссылкой на созданный Job, или поиск через `GET /jobs?reportId=…&periodFrom=…`. [openapi.yaml](api/openapi.yaml): `runReport`, `listJobs`; [ADR-0002](adr/0002-duplicate-request-protection.md)                                                                                                                                                                                                                                                                                                                                                                                  |
| **К3 Неизвестная операция**        | Неизвестный путь — `404 not_found`, неизвестный метод — `405 method_not_allowed`, неизвестное поле в теле — `400 validation_failed` с `fields[].code = unknown_field`, неизвестный канал или период — `400` (`invalid_value`, поля — `enum`). Job не создаётся. Внутри: шаг без Tool — `unknown_operation`, Job → `Failed`. [openapi.yaml](api/openapi.yaml): раздел «Общие правила», `ErrorCode`; [tool-contract.md](tool-contract.md): `IToolRegistry`, раздел «Кто проверяет параметры»                                                                                                                                                                                                                                      |
| **К4 Кривые параметры**            | `400 validation_failed`, в `fields` — все ошибки сразу: путь к полю (`panelIds[2]`, `delivery.email.recipients[1]`) и код (`required`, `invalid_type`, `out_of_range`, …). Кривой JSON — `400 malformed_json`. Ничего не сохраняется, Job не создаётся. Параметры шагов проверяет сам Tool методом `Validate` ещё при сохранении отчёта. [openapi.yaml](api/openapi.yaml): ответ `ValidationFailed`, схемы `Error`, `FieldError`; [tool-contract.md](tool-contract.md): «Кто проверяет параметры»                                                                                                                                                                                                                               |
| **К5 Воскрешение**                 | Финальные состояния неизменны: `cancel` / `approve` / `reject` завершённого Job → `409 invalid_transition`, `details.allowedActions: []`. Повторный запуск за тот же период — `POST /reports/{reportId}/jobs` создаёт **новый** Job; прежний Job, его журнал и файл остаются. [architecture.md](architecture.md#запрещённые-переходы): первая строка таблицы; [openapi.yaml](api/openapi.yaml): `runReport`; [ADR-0002](adr/0002-duplicate-request-protection.md)                                                                                                                                                                                                                                                               |
| **К6 Отмена**                      | `POST /jobs/{jobId}/cancel` из `Scheduled`, `Collecting`, `Narrating`, `Retrying`, `AwaitingApproval` → `200`, Job `Cancelled`; Tool получает `CancellationToken`, собранные данные и PDF удаляются, в каналы ничего не уходит. Из `Aggregating`, `Rendering` (шаги на секунды) и `Delivering` (письмо не отозвать) — `409 invalid_transition`. [openapi.yaml](api/openapi.yaml): `cancelJob`; [architecture.md](architecture.md#запрещённые-переходы)                                                                                                                                                                                                                                                                          |
| **К7 Огромный вход**               | Тело больше 64 КБ — `413 payload_too_large`. Лимиты полей: до 50 панелей, 50 получателей, 30 переменных, период до 366 дней → `400` с `too_many_items` / `out_of_range`. Данные из Grafana больше 10 000 точек в ряду или 50 МБ → Tool отказывает `input_too_large`, Job → `Failed` с `error.code`. PDF больше 20 МБ не уходит письмом (`input_too_large` в канале email), MinIO принимает до 100 МБ. [openapi.yaml](api/openapi.yaml): «Общие правила», `ReportInput`, `RunReportInput`; [tool-contract.md](tool-contract.md): `grafana.collect`, `delivery.minio`, `delivery.email`                                                                                                                                           |
| **К8 Чужой или несуществующий id** | Отчёт, Job или файл, к которым нет доступа, неотличимы от несуществующих: `404 not_found` с одинаковым телом, существование чужого ресурса не раскрывается (SC-4). `403 forbidden` — только когда ресурс доступен, но роль не позволяет действие. Идентификаторы случайные (`job_01JD3M2V7K`), не последовательные — перебором не угадать. [openapi.yaml](api/openapi.yaml): раздел «Доступ», ответы `NotFound`, `Forbidden`, `downloadReportFile`                                                                                                                                                                                                                                                                              |
| **К9 Перезапуск сервера**          | Состояние Job хранится в PostgreSQL, а не в памяти. После перезапуска Worker Hangfire заново выдаёт незавершённый шаг; Job всё это время в состоянии шага (например, `Collecting`), шаг выполняется повторно — Tool идемпотентны. Если старый и новый воркер выполнят шаг одновременно, условный `UPDATE` с версией пропустит только один переход. Перезапуск Api ничего не теряет. [ADR-0001](adr/0001-background-jobs-hangfire.md); [architecture.md](architecture.md#запрещённые-переходы): последняя строка; [tool-contract.md](tool-contract.md): «Обязательства Tool»                                                                                                                                                     |
| **К10 Внешний сервис**             | Grafana молчит 30 с или отвечает `5xx` → `upstream_unavailable` (`Transient`) → Job `Retrying`, повтор через 30 с / 2 мин / 8 мин / 15 мин / 15 мин (окно ~40 мин), затем `Failed` и уведомление. Мусор вместо JSON или переименованное поле → `upstream_bad_response` (`Permanent`) → сразу `Failed`: повтор не поможет. Клиент видит в `GET /jobs/{jobId}` состояние, `attempt`, `nextAttemptAt` и `error` (`code`, `step`). При сохранении отчёта — `502 grafana_unavailable` с `Retry-After`, ничего не сохранено. MinIO и SMTP — так же, коды `storage_unavailable`, `smtp_unavailable`. [tool-contract.md](tool-contract.md): `grafana.collect`, таблица «Какими ошибками отказывает»; [openapi.yaml](api/openapi.yaml): `GrafanaUnavailable`, схема `Job` |

## Что предложил ИИ

Дали модели контракт (`openapi.yaml`, `tool-contract.md`, диаграмму состояний, ADR-0001, ADR-0002) и колоду К1–К10
и попросили сыграть атакующего.

### Промпт

```
Ты — атакующий в игре «контрактный покер». Твоя цель — найти ситуации,
на которые контракт сервиса НЕ отвечает: защитник не сможет показать строку
в контракте, где написан ответ.

Сервис: Grafana Reports — строит PDF-отчёты по панелям Grafana по расписанию
и вручную, доставляет на почту и в MinIO. Job проходит состояния
Scheduled → Collecting → Aggregating → Rendering → (AwaitingApproval) →
Delivering → Delivered / PartiallyDelivered / Failed / Cancelled, с Retrying.

Контракт:
<openapi.yaml целиком>
<tool-contract.md целиком>
<раздел «Диаграмма состояний Job» из architecture.md>
<ADR-0001 и ADR-0002>

Колода уже разыграна, ответы на карты К1–К10:
<таблица выше>

Найди ещё 3 ситуации, которые НЕ покрыты ни одной картой и на которые контракт
не отвечает. Для каждой:
1. Конкретный запрос или последовательность запросов (с телами и заголовками).
2. Что сейчас произойдёт по контракту и где контракт молчит.
3. Чем это опасно: утечка данных, дубль доставки, зависший Job, неверный отчёт.
4. Как бы ты закрыл дыру — минимальная правка контракта.

Не повторяй карты К1–К10 в другой формулировке. Предпочитай гонки,
утечки и тихие ошибки громким падениям.
```

### Находка 1. Один `Idempotency-Key` у разных пользователей или операций

**Что нашла модель.** Пользователь A запускает отчёт с ключом `k1`, пользователь B (или интеграция с захардкоженным
ключом) отправляет `POST /reports` с тем же `k1`. Контракт не говорил, в какой области уникален ключ: если ключ
глобальный, B получит `422 idempotency_key_mismatch` или, хуже, «повтор» чужого ответа — с чужим Job и данными отчёта.

**Решение: приняли.** Ключ уникален в паре «пользователь + операция». Изменили описание параметра `Idempotency-Key`
в [openapi.yaml](api/openapi.yaml) и первичный ключ таблицы `idempotency_keys` в
[ADR-0002](adr/0002-duplicate-request-protection.md): `(user_id, operation, key)`.

### Находка 2. Одобрение в момент истечения срока одобрения

**Что нашла модель.** Job в `AwaitingApproval`, срок одобрения истекает в 12:00:00. В 11:59:59.900 владелец отправляет
`POST /jobs/{jobId}/approve`, одновременно таймер переводит Job в `Cancelled`. Контракт описывает каждый переход
по отдельности, но не говорит, кто выигрывает и что увидит владелец: «одобрил, а отчёт не ушёл» без объяснения.

**Решение: приняли.** Переходы уже условные (`UPDATE … WHERE state = @expected AND version = @version`), выигрывает
первый записанный. Дописали в описание `approveJob` в [openapi.yaml](api/openapi.yaml): проигравший `approve`
получает `409 invalid_transition` с `currentState: Cancelled`, а в `job_events` — событие с причиной
`approval_timeout`, чтобы владелец видел, почему отчёт не ушёл.

### Находка 3. Лавина ручных запусков

**Что нашла модель.** Скрипт владельца вызывает `POST /reports/{reportId}/jobs` для каждого дня за последние
3 года — 1095 разных периодов, у всех разные ключи, ни один не конфликтует с другим. Контракт не ограничивает частоту
запусков: очередь забивается, плановые отчёты других команд задерживаются, Grafana получает тысячи запросов.

**Решение: не приняли.** Пользователи сервиса — сотрудники с учётными записями, внешних анонимных клиентов нет.
Нагрузку на Grafana ограничивает число воркеров Hangfire (параллельно выполняется не больше N шагов), а не частота
запросов к API: лавина только удлиняет очередь, но не роняет Grafana. Каждый запуск остаётся в `job_events`
с автором, такой скрипт будет заметен оператору, а незапущенные Job он может отменить. `429` и квоты добавим,
если появятся внешние интеграции с правом запуска — это условие пересмотра в
[ADR-0001](adr/0001-background-jobs-hangfire.md) (нагрузка больше ~1000 Job в час).
