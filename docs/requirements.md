# Requirements

## Сценарии

Шесть сценариев: четыре основных и два ошибочных. Основной сценарий сервиса — SC-2. Критерии приёмки записаны в формате `Дано / Когда / Тогда`.

### SC-1. Настройка отчёта

**Цель:** описать, какие данные, за какой период и куда отправлять.

**Участник:** владелец отчёта.

1. Владелец указывает `uid` дашборда Grafana и выбирает панели.
2. Задаёт значения переменных шаблона (например, `$env = prod`).
3. Выбирает период (день, неделя, месяц), расписание cron и часовой пояс.
4. Выбирает каналы доставки: почта (список адресатов), MinIO или оба; при необходимости включает ручное одобрение.
5. Сервис проверяет доступ к дашборду и наличие панелей, сохраняет отчёт и создаёт расписание.

**Критерии приёмки:**

- **Дано** дашборд с указанным `uid` существует и сервисный аккаунт имеет к нему доступ, **когда** владелец сохраняет отчёт, **тогда** отчёт сохраняется, а `RecurringJob` создаётся с указанными cron и часовым поясом.
- **Дано** одна из выбранных панелей отсутствует на дашборде, **когда** владелец сохраняет отчёт, **тогда** сервис отвечает `422` со списком отсутствующих панелей и ничего не сохраняет.
- **Если** не выбран ни один канал доставки, **то** сервис должен отклонить сохранение с ошибкой валидации.

### SC-2. Плановый запуск и доставка отчёта (основной)

**Цель:** получатели вовремя получают отчёт за прошедший период без ручной работы.

**Участник:** система (планировщик); получатели — пассивно.

1. Наступает время расписания, сервис создаёт Job в состоянии `Scheduled` и вычисляет границы периода из запланированного времени.
2. `Collecting`: сервис читает описание дашборда, подставляет переменные и период и запрашивает данные панелей.
3. `Aggregating`: считает итоги и сравнение с прошлым периодом.
4. `Rendering`: строит графики и собирает PDF.
5. При включённом одобрении Job ждёт в `AwaitingApproval`, пока владелец не подтвердит отправку.
6. `Delivering`: файл кладётся в MinIO и/или отправляется письмом.
7. Job переходит в `Delivered`, ключ объекта записывается в `report_files`.

**Критерии приёмки:**

- **Когда** наступает запланированное время отчёта, сервис должен создать ровно один Job на пару «отчёт + период».
- **Дано** отчёт с периодом «неделя» и часовым поясом `Asia/Yekaterinburg`, **когда** запуск происходит в понедельник в 09:00, **тогда** данные запрашиваются за предыдущие понедельник 00:00 — воскресенье 23:59:59 по этому поясу.
- **Когда** доставка в MinIO завершилась успешно, сервис должен записать ключ объекта в `report_files` до перехода Job в `Delivered`.
- **Пока** Job находится в `AwaitingApproval`, сервис не должен отправлять отчёт ни в один канал.

### SC-3. Ручной запуск за произвольный период

**Цель:** получить отчёт вне расписания — за прошлый период или пересобрать упавший.

**Участник:** владелец отчёта или оператор.

1. Пользователь вызывает запуск отчёта через API с границами периода.
2. Сервис создаёт Job в `Scheduled` с пометкой «ручной».
3. Дальше Job проходит те же шаги, что в SC-2.
4. Пользователь отслеживает статус по истории переходов Job.

**Критерии приёмки:**

- **Дано** для этого отчёта и периода уже есть Job в незавершённом состоянии, **когда** пользователь запускает отчёт вручную, **тогда** сервис отвечает `409` со ссылкой на существующий Job.
- **Если** конец периода позже текущего времени, **то** сервис должен отклонить запуск с ошибкой валидации.

### SC-4. Выгрузка отчёта из хранилища

**Цель:** забрать готовый отчёт без доступа к почте.

**Участник:** получатель или внешняя система.

1. Клиент запрашивает список файлов отчёта за нужный период.
2. Сервис возвращает метаданные: период, дата создания, размер, Job.
3. Клиент запрашивает выгрузку файла.
4. Сервис отдаёт файл потоком или presigned URL с коротким сроком действия.

**Критерии приёмки:**

- **Дано** у клиента есть право чтения отчёта, **когда** он запрашивает выгрузку, **тогда** сервис возвращает файл или presigned URL со сроком действия не больше настроенного.
- **Дано** у клиента нет права чтения отчёта, **когда** он запрашивает список или файл, **тогда** сервис отвечает `403` и не раскрывает, существует ли файл.
- **Если** объект удалён из MinIO по lifecycle-политике, **то** сервис должен отвечать `410` и помечать запись в `report_files` как удалённую.

### SC-5. Grafana недоступна при плановом запуске (ошибочный)

**Цель:** временный сбой не теряет отчёт, а затяжной — не остаётся незамеченным.

**Участник:** система; оператор и владелец получают уведомление.

1. На шаге `Collecting` Grafana отвечает `5xx` или не отвечает за таймаут.
2. Job переходит в `Retrying`, повтор планируется с увеличивающейся задержкой.
3. Если Grafana восстановилась, Job продолжает с `Collecting`, как в SC-2.
4. Если попытки исчерпаны, Job переходит в `Failed`, владельцу и оператору уходит уведомление.

**Критерии приёмки:**

- **Если** Grafana вернула `5xx` или запрос превысил таймаут, **то** сервис должен перевести Job в `Retrying` и запланировать повтор с backoff.
- **Дано** лимит попыток исчерпан, **когда** очередная попытка завершилась ошибкой, **тогда** Job переходит в `Failed`, в `job_events` записывается последняя ошибка, а владелец получает уведомление.
- **Пока** Job находится в `Retrying`, сервис не должен ничего доставлять получателям.

### SC-6. Дашборд изменён, доставка частично не удалась (ошибочный)

**Цель:** не отправлять неверный отчёт и не терять уже доставленное.

**Участник:** система; владелец отчёта.

1. На шаге `Collecting` выясняется, что панель удалена или сервисный аккаунт потерял доступ (`401`/`403`/`404`).
2. Ошибка считается неустранимой: Job сразу переходит в `Failed` без ретраев, владелец получает уведомление с причиной.
3. В другом запуске отчёт собран, но при доставке MinIO принял файл, а SMTP-сервер отказал.
4. Сервис повторяет доставку только в упавший канал; после исчерпания попыток Job переходит в `PartiallyDelivered`.

**Критерии приёмки:**

- **Если** Grafana вернула `401`, `403` или `404` для дашборда или панели, **то** сервис должен перевести Job в `Failed` без повторных попыток и указать в уведомлении отсутствующую панель или причину отказа.
- **Дано** доставка в MinIO прошла, а фича-флаг доставки в почту включен и письмо не отправлено, **когда** сервис повторяет доставку, **тогда** повторяется только отправка письма, а файл в MinIO не перезаписывается.
- **Дано** попытки отправить письмо исчерпаны, **когда** завершается шаг доставки, **тогда** Job переходит в `PartiallyDelivered`, а статус каждого канала виден в истории Job.

## Жизненный цикл Job

Переход, которого нет в списке, сервис отклоняет как ошибку. Из финальных состояний переходов нет: повторный запуск создаёт новый Job.

**Состояния:**

- `Scheduled` — Job создан, ждёт воркер.
- `Collecting` — запрос данных панелей в Grafana.
- `Aggregating` — расчёт итогов и сравнения с прошлым периодом.
- `Narrating` — текстовый вывод от LLM (необязательный, после первой версии).
- `Rendering` — графики и PDF.
- `AwaitingApproval` — ожидание подтверждения владельца (необязательный).
- `Delivering` — доставка в каналы.
- `Retrying` — ожидание повтора после временной ошибки.
- `Delivered` — финальное: доставлено во все каналы.
- `PartiallyDelivered` — финальное: доставлено не во все каналы.
- `Failed` — финальное: неустранимая ошибка или исчерпаны попытки.
- `Cancelled` — финальное: отменён пользователем или отклонён при одобрении.

**Разрешённые переходы:**

- `Scheduled` → `Collecting` | `Cancelled`
- `Collecting` → `Aggregating` | `Retrying` (временная ошибка) | `Failed` (`401`/`403`/`404`) | `Cancelled`
- `Aggregating` → `Narrating` (LLM включён) | `Rendering` (LLM выключен) | `Failed`
- `Narrating` → `Rendering` (текст готов или шаг упал — отчёт идёт без текста) | `Cancelled`
- `Rendering` → `AwaitingApproval` (одобрение включено) | `Delivering` | `Retrying` | `Failed`
- `AwaitingApproval` → `Delivering` (одобрено) | `Cancelled` (отклонено или истёк срок)
- `Delivering` → `Delivered` | `PartiallyDelivered` | `Retrying` | `Failed` (не доставлено ни в один канал)
- `Retrying` → шаг, на котором произошла ошибка (`Collecting`, `Rendering` или `Delivering`) | `Failed` (попытки исчерпаны) | `Cancelled`

### Предложение 1. Пустые или неполные данные выглядят как нормальный отчёт

**Описание.** Grafana отвечает `200`, но фреймы пустые или с дырами: источник лежал часть периода, у Prometheus срок хранения короче месячного периода, экспортёр метрик был выключен. Сервис честно считает итоги по тому, что есть, и отправляет отчёт с нулями или заниженными цифрами. Job в `Delivered`, ошибок нет, получатели делают неверные выводы.

**Мера.** На шаге `Aggregating` проверять покрытие периода по каждой панели. Если покрытие ниже порога из настроек отчёта, помечать панель в PDF как «данные неполные»; если данных нет совсем — переводить Job в `AwaitingApproval` даже без включённого одобрения. Критерий: *если покрытие периода данными панели ниже порога, то сервис должен пометить панель в отчёте и записать покрытие в `job_events`.*

**Решение: принять.** Здесь тихий тип сбоя, и он не ловится ни ретраями, ни статусами. Проверка дешёвая: данные уже в памяти на шаге агрегации.

### Предложение 2. Цифры в отчёте не совпадают с дашбордом

**Описание.** API Grafana возвращает сырые данные запроса. Трансформации панели, вычисление `Reduce` (last, mean, max), единицы измерения и overrides Grafana применяет во фронтенде. Сервис посчитает «среднее», а на дашборде у той же панели стоит «последнее значение» в другой единице — получатель видит два разных числа и перестаёт доверять отчёту.

**Мера.** Читать из JSON панели способ свёртки (`reduceOptions.calcs`) и единицы (`fieldConfig.defaults.unit`) и применять их при агрегации. Панели с трансформациями, которые сервис не поддерживает, отклонять при сохранении отчёта (SC-1) с понятной ошибкой. Критерий: *когда панель содержит неподдерживаемую трансформацию, сервис должен отклонить сохранение отчёта и назвать трансформацию.*

**Решение: принять частично.** Свёртку, единицы и проверку при сохранении принимаем: это дёшево и закрывает самые частые расхождения. Полную реализацию движка трансформаций Grafana отклоняем, интегрироваться с функциональностью фронтенда Grafana намерений не имеем.

### Предложение 3. Шаг выполняется дважды параллельно

**Описание.** Hangfire гарантирует выполнение «хотя бы один раз». Если воркер перезапустился посреди шага или шаг шёл дольше таймаута невидимости хранилища Hangfire, задачу возьмёт другой воркер, пока первый ещё работает. Два экземпляра одного шага одновременно пишут в один Job: переходы в `job_events` идут вперемешку, а доставка может уйти дважды.

**Мера.** Каждый переход Job делать условным: `UPDATE jobs SET state = @next, version = version + 1 WHERE id = @id AND state = @expected AND version = @version` (concurrency token в EF Core). Шаг, который не смог выполнить переход, завершается без побочных эффектов. Таймаут невидимости задать больше максимальной длительности шага. Критерий: *если переход Job выполняется из состояния, отличного от ожидаемого, то сервис должен отклонить переход и не выполнять доставку.*

**Решение: принять.** Без реализации описанного все остальные гарантии (идемпотентность доставки, история переходов) держатся на удаче. Мера почти бесплатна, если заложить её в движок сразу.
