# ADR-0001. Фоновый запуск Job через Hangfire, состояние Job — в своих таблицах

- **Дата:** 2026-11-15
- **Статус:** принято
- **Участники:** КуксовскийИЕ, КучинСМ

## Контекст и ограничения

- Построение отчёта занимает от секунд до нескольких минут: запросы к Grafana по каждой панели, расчёт, рендер PDF,
  доставка. При ретраях (SC-5) и ожидании одобрения (SC-2) Job живёт часы, а `AwaitingApproval` — до суток.
- HTTP-запрос не может ждать столько: клиент получит таймаут, а запрос потеряется при перезапуске (карты К2, К9).
- Job должен переживать перезапуск процесса и продолжать с того шага, на котором остановился.
- Нужны отложенные повторы с backoff и расписание по cron с часовым поясом.
- Жизненный цикл Job — свой (12 состояний, `AwaitingApproval`, `PartiallyDelivered`), каждый переход пишется
  в `job_events` ([requirements.md](../requirements.md#жизненный-цикл-job)).
- Команда — два человека, стек .NET, PostgreSQL в проекте уже есть. Новую инфраструктуру поддерживать некому.

## Решение

1. Два процесса из одного репозитория: **Api** принимает запросы, **Worker** выполняет шаги.
   API только создаёт Job в `Scheduled`, ставит шаг в очередь и сразу отвечает `202`.
2. Очередь, отложенные повторы и cron — **Hangfire** с хранилищем в той же **PostgreSQL**.
   Каждый шаг Job — отдельная задача Hangfire; Dispatcher после шага ставит следующий.
3. **Источник правды о Job — наши таблицы** `jobs` и `job_events`, а не состояния Hangfire.
   Hangfire только «будит» Dispatcher. Встроенные ретраи Hangfire выключены (`AutomaticRetry(Attempts = 0)`):
   повторять или нет, решает Dispatcher по виду ошибки Tool ([tool-contract.md](../tool-contract.md)).
4. Переход Job — условный `UPDATE jobs SET state = @next, version = version + 1
   WHERE id = @id AND state = @expected AND version = @version`. Не прошёл — шаг завершается без побочных эффектов.
5. После перезапуска Worker Hangfire заново выдаёт незавершённые шаги (по таймауту невидимости). Job всё это время
   остаётся в состоянии своего шага (например, `Collecting`), шаг выполняется повторно — поэтому каждый Tool идемпотентен.

## Рассмотренные альтернативы

| Вариант                                                  | Почему не выбран                                                                                                                                                                                                         |
|----------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Синхронно в HTTP-запросе                                 | Таймауты клиента и прокси, Job теряется при перезапуске, нет отложенных повторов                                                                                                                                         |
| `BackgroundService` + `Channel<T>` в памяти процесса Api | Очередь теряется при перезапуске, нет отложенных задач и cron, Api и выполнение не масштабируются отдельно                                                                                                               |
| RabbitMQ / Kafka и отдельные сервисы на каждый шаг       | Ещё одна система в инфраструктуре и сетевые контракты между сервисами; для двух человек и десятков отчётов в день — избыточно                                                                                            |
| Состояние Job = состояние задачи Hangfire                | Состояния Hangfire (`Enqueued`, `Processing`, `Succeeded`, `Failed`) не покрывают наш жизненный цикл: нет `AwaitingApproval`, `PartiallyDelivered`, журнала переходов; правило переходов оказалось бы в чужой библиотеке |
| Quartz.NET                                               | Умеет cron, но очередь и повторы пришлось бы строить самим; у Hangfire это есть из коробки                                                                                                                               |

## Цена решения

- **Два места, где живёт состояние** (Hangfire и `jobs`), их нужно держать согласованными: задача Hangfire
  может быть, а Job уже `Cancelled` — Dispatcher обязан проверять состояние Job перед каждым шагом.
- **Доставка «хотя бы один раз»**: шаг может выполниться дважды, поэтому все Tool обязаны быть идемпотентными,
  а переходы — условными. Это дополнительный код и тесты на каждый Tool.
- **PostgreSQL как очередь**: Hangfire опрашивает базу, это нагрузка на ту же БД, где лежат отчёты.
- Worker зависит от Hangfire; ядро (`Domain`, `Engine`) — нет, Hangfire подключается только в процессе Worker.
- Письмо может уйти дважды, если SMTP принял его, а ответ потерялся до записи статуса канала.

## Условия пересмотра

- Нагрузка больше ~1000 Job в час или задержка между шагами больше минуты из-за опроса БД.
- Шаги понадобится выполнять в разных сервисах или на разных языках (например, рендер в отдельном контейнере).
- Hangfire перестанет поддерживаться или нужные функции уйдут в платную версию.
- Нагрузка очереди начнёт мешать основным запросам к PostgreSQL.
