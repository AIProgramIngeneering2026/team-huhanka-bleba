# ADR-0002. Защита от повторного запроса: Idempotency-Key и один незавершённый Job на «отчёт + период»

- **Дата:** 2026-11-15
- **Статус:** принято
- **Участники:** КуксовскийИЕ, КучинСМ

## Контекст и ограничения

- Пользователь может дважды нажать «Запустить» (К1) или не получить ответ из-за таймаута и повторить запрос (К2).
- Плановый и ручной запуск за один и тот же период могут совпасть; после перезапуска Worker Hangfire может
  вызвать `RecurringJob` повторно.
- Требования: «ровно один Job на пару отчёт + период» (SC-2), `409` со ссылкой на существующий Job при ручном
  запуске (SC-3). Дубль Job — это дубль письма руководству.
- Получатели отчёта и внешние системы ходят в API напрямую, не только через наш клиент.
- Дополнительную инфраструктуру (Redis и т. п.) не хотим — см. ADR-0001.

## Решение

Два независимых уровня защиты.

**1. Уникальность незавершённого Job.** Частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX ux_jobs_active_period
    ON jobs (report_id, period_from, period_to)
    WHERE state NOT IN ('Delivered', 'PartiallyDelivered', 'Failed', 'Cancelled');
```

- Ручной запуск при конфликте — `409 job_already_active`, `details.jobId` и `Location` на существующий Job
  ([openapi.yaml](../api/openapi.yaml), операция `runReport`).
- Планировщик при конфликте молча пропускает запуск и пишет предупреждение в лог.
- После завершения Job запуск за тот же период разрешён и создаёт **новый** Job (К5).

**2. Заголовок `Idempotency-Key`** у `POST /reports` и `POST /reports/{reportId}/jobs`:

- Таблица `idempotency_keys(user_id, operation, key, request_hash, status_code, response_body, created_at)`,
  первичный ключ — `(user_id, operation, key)`. Ключ одного пользователя или одной операции не пересекается
  с другим.
- Тот же ключ и то же тело — прежний ответ с кодом `200` и `Idempotent-Replayed: true`, ничего не создаётся.
- Тот же ключ и другое тело — `422 idempotency_key_mismatch`.
- Ключи хранятся 24 часа, потом удаляются фоновой задачей.
- Сгенерированный клиент API всегда отправляет ключ; для сторонних клиентов ключ необязателен.

## Рассмотренные альтернативы

| Вариант                                 | Почему не выбран                                                                                                                     |
|-----------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------|
| Только уникальный индекс, без ключа     | Повтор после потерянного ответа получает `409` вместо исходного ответа — клиенту нужно разбирать ошибку; не защищает `POST /reports` |
| Только `Idempotency-Key`                | Не защищает от совпадения планового и ручного запуска и от повторного срабатывания расписания — у них нет общего ключа               |
| Блокировка кнопки на клиенте (debounce) | Не помогает при потерянном ответе и при вызовах из сторонних систем                                                                  |
| Распределённая блокировка в Redis       | Новая система в инфраструктуре ради одной проверки, которую делает индекс PostgreSQL                                                 |
| Ключ идемпотентности обязательный       | Ломает простые интеграции (`curl`, BI-системы); защита от дубля Job и без него есть на уровне индекса                                |

## Цена решения

- Ещё одна таблица, задача её очистки и хранение тел ответов (до 64 КБ на ключ).
- `POST /reports` без ключа при двойном клике создаст два отчёта — сознательно: отчёт без расписания не рассылает
  ничего сам по себе, дубль виден в списке и удаляется. Наш клиент всегда шлёт ключ.
- После 24 часов повтор с тем же ключом создаст новый Job (если прежний завершён) — клиент должен смотреть
  `GET /jobs?reportId=…&periodFrom=…`.
- Индекс завязан на список финальных состояний: новое финальное состояние — миграция индекса.

## Условия пересмотра

- Появятся внешние клиенты, которые массово повторяют запросы без ключа и создают дубли отчётов.
- Таблица ключей вырастет настолько, что начнёт влиять на производительность БД.
- Понадобится идемпотентность для `PUT`, `approve` и других операций.
- Понадобится несколько незавершённых Job на один период (например, разные наборы получателей).
